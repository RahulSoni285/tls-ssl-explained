DNS · TLS · SSL, in order

Every secure connection starts with a handshake.

Before a browser and a server exchange a single byte of your data, they run a quiet negotiation: find the address, prove identity, agree on a secret. This page walks through that negotiation piece by piece — then lets you flip the lights off and see what happens without it.

~1 extra round trip for a full TLS 1.3 handshake
Domain-validated certificates, proven over DNS
0 readable bytes for an eavesdropper on HTTPS

Three letters, three jobs

They get used interchangeably. They're not the same thing.

DNS · Domain Name System

Finds the address

Translates a name like example.com into an IP address the network can actually route to. It's a phone book — it does not encrypt anything or prove who's on the other end.

TLS · Transport Layer Security

Builds the secure tunnel

The modern protocol that authenticates the server, negotiates a shared secret, and encrypts everything sent afterward. This is the thing actually doing the work today.

SSL · Secure Sockets Layer

TLS's retired predecessor

SSL came first and was formally deprecated years ago for security flaws. "SSL certificate" stuck around as everyday shorthand, but the certificate and handshake in use today are TLS.

Step zero

Before TLS can start, the browser has to find the server

Typing a URL kicks off a DNS lookup, resolving the hostname to an IP address, so the browser knows where to send the connection it's about to open.

Browsertypes example.com
DNS resolverreturns 93.184.216.34
DNS only answers "where is it?" — it doesn't answer "can I trust it?" That second question is what the certificate and TLS handshake are for, and it's also where DNS shows up again, in a different role: proving domain ownership to a Certificate Authority.

How a certificate gets issued

Proving example.com actually belongs to you

Anyone can generate a key pair. A Certificate Authority (CA) will only sign a certificate for a domain once you've proven you control it — and for the most common certificate type, that proof happens over DNS.

1

Request a certificate

The site owner (usually through automation like Certbot or a hosting platform) asks a CA — say, Let's Encrypt — to issue a certificate for example.com.

2

CA issues a challenge

The CA generates a random token and hands back a challenge: place this exact value somewhere only the domain's real owner could put it.

DNS-01 challenge · random token issued
3

Owner publishes the proof

The owner adds a TXT record at _acme-challenge.example.com containing that token — something only someone with control of the domain's DNS could do.

_acme-challenge.example.com TXT "8f3a2c9e..."
4

CA queries DNS to check

The CA looks up that TXT record itself. If the value matches the token it issued, domain control is confirmed — no human review needed.

5

Certificate signed and issued

The CA signs a certificate binding the domain name to the site's public key, then chains it up to a root certificate every browser already trusts.

This is domain validation (DV) — it confirms control of the domain, nothing more. Other certificate types (organization- or extended-validation) add real-world identity checks on top, but the DNS or HTTP proof-of-control step is the foundation almost every certificate rests on.

Recap

The four ideas worth keeping

01

DNS finds it

Resolves a name to an address. No encryption, no identity check — that's not its job.

02

A CA proves it

Certificates are issued after proving domain control, often via a DNS TXT record challenge.

03

TLS secures it

The handshake authenticates the server and agrees a session key before any real data moves.

04

Termination decides who holds the key

Whether encryption ends at your edge or your app server changes what's protected on your own network.

Phase 01 · Resolve

Turning "google.com" into an address

Nothing gets requested until something local to you can name an IP address. The browser checks in order, cheapest and closest first, and stops the moment something answers.

1

Browser checks its own cache

Chrome and Firefox keep a short-lived DNS cache and an HSTS list of hosts that must always be reached over HTTPS. google.com is HSTS-preloaded, so the browser already knows to skip plain HTTP entirely, before any lookup even runs.

cached → skip ahead to connectingnot cached → keep looking
2

Operating system checks the hosts file

Before asking anyone else, the OS reads a local text file for a manual override — /etc/hosts on macOS and Linux, C:\Windows\System32\drivers\etc\hosts on Windows. Almost always empty for a public domain, but it's exactly how local development, and occasionally malware, redirects a name.

entry found → use it, doneno entry → keep looking
3

OS-level resolver cache

The operating system's own stub resolver keeps a short-term cache of recent lookups, separate from the browser's.

cached → return the stored IPnot cached → keep looking
4

Query reaches a recursive resolver

The OS hands the question to a recursive resolver — usually your ISP's, or a public one you've configured, like 8.8.8.8 or 1.1.1.1. This resolver keeps its own cache too, and in practice a large share of everyday lookups stop right here.

cached → return the stored IPnot cached → ask the DNS hierarchy
5

Resolver asks a root server

Cache empty, so the resolver starts at the top of the tree: one of the root server clusters. Root servers don't know google.com's address — but they know exactly who's authoritative for .com.

response: a referral, not an answer
6

.com registry points the way

The root server refers the resolver to the .com TLD nameservers. They don't hold the IP either, but they know which nameservers are authoritative for google.com specifically, and refer the query onward.

7

Authoritative nameserver returns the address

Google's own nameservers hold the real record and return it — an IP address such as 142.250.xxx.14, plus a TTL. The resolver caches that answer for as long as the TTL allows, then hands it back up through the OS to the browser.

Phase 03 · Secure

The TLS handshake runs

This is the exact negotiation from the interactive walkthrough earlier on this page: a ClientHello, the server's certificate checked up its trusted chain (the same chain proven by DNS at issuance time), and a shared session key agreed without ever sending that key across the wire. TLS 1.3 often folds this into the same round trip as the TCP handshake above, so the connection is open and encrypted almost simultaneously. ↑ replay the interactive handshake

ClientHello→ Certificate presented→ Chain verified→ Session key agreed→ Connection encrypted

Phase 04 · Request

The page actually gets requested

Only now does the browser send GET / HTTP/2, along with cookies and headers, inside the TLS session just negotiated. The server responds with the page's HTML. As the browser parses it, it discovers everything else the page needs — stylesheets, scripts, images, fonts — often hosted on entirely different domains, like fonts.gstatic.com. Each new domain can mean the whole resolve → connect → secure sequence runs again, though HTTP/2 lets many requests to the same origin share one already-open connection instead of opening a new one each time.

Phase 05 · Render

Bytes become a page

The browser turns the HTML into a DOM tree and the CSS into a CSSOM, combines the two into a render tree, works out where everything sits, and finally paints pixels to the screen.

HTML → DOM+ CSS → CSSOM→ Render tree→ Layout→ Paint
Start to finish, a first-ever visit means a cache miss at every local level, a full DNS referral chain, a TCP handshake, and a TLS handshake — all before the first byte of the actual request leaves the browser. Visit the same site again and most of Phase 01 simply disappears: the browser's own cache, or the resolver's, already has the answer.

Diagrams are simplified for clarity — real handshakes and validation flows include additional messages, extensions, and edge cases.
